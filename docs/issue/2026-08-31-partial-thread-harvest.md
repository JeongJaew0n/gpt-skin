# 긴 대화를 열면 앞쪽 메시지가 스크롤백에서 빠진다

- 상태: **해결** (2026-09-01) — DOM 대신 백엔드에서 대화 원본을 읽는다
- 관련 파일: `src/content/store.js`, `src/content/index.js`, `src/main/tap.js`

## 증상

대화를 열면 앞부분 턴이 스크롤백에 나타나지 않는다.
`:reload` 하거나 사이드바를 통해 다시 들어가면 나타나기도 한다.

## 무엇을 확인했나

테스트 대화(사용자 3턴 + 응답 3턴 = 6턴)로 측정했다.

| 조건 | 렌더된 `conversation-turn` |
|---|---|
| `/c/<id>` **콜드 로드** | **5개** (turn-1 없음) |
| 콜드 로드 후 32초 대기 | 5개 — 늘지 않음 |
| 스레드 스크롤러를 맨 위로 | 5개 — 늘지 않음 |
| 사이드바에서 **SPA 이동** | **6개** (전부) |

**원본 ChatGPT 가 진입 경로에 따라 턴을 다 그리지 않는다.** 우리 확장과 무관하다:
`gpt-skin-on` 클래스를 떼고 원본 UI 를 3초 노출해도 5개 그대로였다.
(오버레이가 `opacity:0` + `overflow:hidden` 이라 원본 측정에 영향을 줬을까 의심해 A/B 로 갈랐다.)

`[확정]` 진입 경로에 따라 DOM 이 다르다.
`[미정]` 왜 그런지 — SSR 윈도잉인지, 하이드레이션 조건인지. 원본 내부라 우리가 고칠 수 없다.

## 우리 쪽 결함 — 이게 진짜 고칠 부분

원본이 불완전한 DOM 을 주는 건 어쩔 수 없다. 문제는 **우리가 그걸 정답으로 믿었다는 것**이다.

**1. 수확이 사실상 한 번뿐이었다**

```js
setTimeout(() => GT.toMain('harvest'), 1200);   // 이게 전부
```

부팅 1.2초 뒤 한 번, 그리고 경로가 바뀔 때. 그 사이 원본이 턴을 더 붙여도 반영되지 않는다.

**2. 수확 결과로 통째로 갈아엎었다**

```js
replaceAll(messages) {
  state.messages = [];      // ← 가진 것을 전부 버린다
  state.byId.clear();
  messages.forEach(upsert);
}
```

부분 수확이 한 번 들어오면 이미 가지고 있던 메시지가 사라진다.
**스트림으로 막 받은 응답도 같이 날아간다** — DOM 에 반영되기 전에 수확이 돌 수 있기 때문이다.
증상이 들쭉날쭉했던 이유다.

## 적용한 것

### `store.applyHarvest()` — 수확을 정답이 아니라 참고로 다룬다

| 상황 | 처리 |
|---|---|
| 대화가 바뀜 (`path` 변경) | 교체 — 이전 대화가 섞이면 안 된다 |
| 수확이 우리가 아는 걸 **전부 포함** | 채택 — DOM 순서를 그대로 쓴다 (늦게 붙은 앞쪽 턴이 여기서 들어온다) |
| 수확이 우리보다 **적게 앎** | 병합 — 가진 것은 지키고 갱신·추가만 한다 |

핵심은 세 번째다. 수확에 없는 메시지는 *삭제된 것*이 아니라 *아직 안 그려진 것*으로 본다.

### 스레드 변화 감시 — 늦게 붙는 걸 잡는다

`#thread` 를 `MutationObserver` 로 보다가 `[data-message-id]` 개수가 바뀌면 400ms 디바운스 후 재수확한다.
SPA 이동이나 지연 마운트로 턴이 더 붙는 순간 스크롤백이 따라간다.

### 곁가지 — 가짜 타임스탬프 제거

수확된 메시지에 `at: Date.now()` 를 찍고 있었다. 화면에는 모든 메시지가 **"46초 전"** 으로 나왔다.
원본 DOM 은 메시지 시각을 노출하지 않는다. 모르는 값을 지어내느니 비우는 게 맞다 —
수확 메시지는 `at: null` 이고 타임스탬프 칸이 빈다. 스트림으로 받은 메시지는 실제 시각을 유지한다.

## 근본 해결 (2026-09-01)

`/backend-api/conversation/<id>` 가 404 였던 건 **인증 헤더가 없어서였다.**
`Authorization: Bearer <accessToken>` (출처 `/api/auth/session`) 을 붙이면 200 이 온다.

이제 DOM 을 정답으로 삼지 않는다. 부팅과 대화 전환 때 백엔드에서 원본을 읽는다.

```
GET /backend-api/conversation/<id>
 → { title, mapping: { <id>: { id, parent, children, message } }, current_node, ... }
```

`current_node` 에서 부모를 따라 올라가면 **지금 보이는 분기**가 나온다.
트리 전체를 훑으면 재생성으로 버려진 분기까지 섞이므로 반드시 이 사슬을 따라야 한다.

측정으로 확인한 효과 — 같은 대화에서:

| | 보이는 메시지 |
|---|---|
| DOM 수확 | 5~6 |
| **API 원본** | **12 (전부)** |

DOM 수확은 폴백으로 남는다. API 가 실패하면(권한·스키마 변경) 예전 경로로 내려간다.
`applyHarvest` 의 병합 규칙도 그대로다 — 스트림으로 막 받은 메시지를 API 응답이 덮지 않는다.

부수 효과로 **메시지 시각을 알게 됐다.** `create_time` 이 있어서
수확 메시지의 타임스탬프가 더 이상 비지 않는다.
