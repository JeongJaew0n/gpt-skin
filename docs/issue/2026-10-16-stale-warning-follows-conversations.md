# '원본이 메시지를 보내지 않았습니다' 가 대화를 옮겨도 계속 보인다

관측: 2026-10-16 · 0.31.2 · 사용자 크롬(로그인 ChatGPT) · 시트 스킨

## 증상

사용자 보고: 새로 만든 대화(`/c/6ad16ff2…`, 생성 2026-10-16 09:29:38 KST)를 가리키며 "자꾸 원본이 메시지를 보내지 않았대".
그 대화에는 사용자 메시지가 하나 있고 답도 정상으로 왔다 — 즉 보낸 것은 보내졌다.

## 확인한 것 `[확정]`

### 1. 사용자 탭의 보고서(`:bug`)

시각은 UTC 로 찍힌다(`bugs.js` 의 `toISOString`). KST 로 옮겨 적는다.

```
gpt-skin 0.31.2 · build 2026-10-15 16:00 · skin sheet
not-sent   2026-10-15 18:59:22 KST   ← 이 탭에서 not-sent 는 이 1건뿐
  composer h=156 (여러 줄 긴 글) · sendButton true · stopButton false · focus true · visible
truncated  2026-10-16 09:30:08 KST   ← 문제의 대화(09:29 생성)의 답. 화면 166 / 원본 196자
truncated  … 그 뒤 5건
```

- 크롬이 확장을 0.31.2 로 다시 읽은 시각: 2026-10-15 16:28:51 KST (Default 프로필 `Secure Preferences` 의 `last_update_time`).
  18:59 의 not-sent 는 0.31.2 에서 난 것이다
- **문제의 대화에서는 not-sent 가 새로 기록되지 않았다.** `bugs.record` 는 바로 앞 기록과 같을 때만 합친다 — 18:59 뒤에 truncated 가 끼어 있으므로 그 뒤 not-sent 가 났다면 새 줄이 생겼어야 한다

### 2. 화면 진단 줄은 대화를 옮겨도 남는다

시트 · 터미널의 `systemLog`(경고 · 명령 결과 줄)는 스킨에 한 벌이고, 지금 보는 대화의 **맨 아래**에 붙여 그린다. 대화를 옮겨도 비우지 않았다(`:clear` · 스킨 해체 때만).

내 탭에서 재현: '세우다' 대화에서 `:version` → 새 채팅 → 시험 대화(`/c/6ad17670…`)로 옮긴 뒤에도 그 대화 맨 아래에
`gpt-skin 0.31.2 · build …` 두 줄이 그대로 있었다.

→ 18:59 에 한 번 뜬 경고가 그 뒤로 여는 모든 대화의 마지막 답 밑에 붙어, 보낼 때마다 실패하는 것처럼 보였다.

### 3. 0.31.2 의 보내기 경로는 세 경우 모두 정상

사용자 승인을 받고 보냄(그 대화 2번 · 새 채팅 1번, 문장 "전송 시험입니다. '네' 한 단어로만 답해 주세요.").
MCP 탭은 뒤에 숨은 탭이라 타이머가 1초 단위로 느려진다 — 그래서 2번째는 '버튼이 뜨는 순간 누르기' 로 앞 탭 타이밍을 흉내 냈다.

| 경우 | 결과 |
|---|---|
| 그 대화 · 스킨 입력줄 Enter | 클릭(trusted false) → submit(trusted true) → 입력창 비움 → 중지 버튼 → 답 끝. 경고 0 |
| 그 대화 · 버튼이 생기는 즉시 클릭(MutationObserver) | 클릭 즉시 입력창 0자 · 63ms 뒤 중지 버튼. 보냄 |
| 새 채팅 · 스킨 입력줄 Enter | `home` 입력창 비움 → 2초쯤 `/c/…` 로 바뀌며 `thread` 입력창으로. 경고 0 |

새 채팅 화면에는 입력창 폼이 둘이다: `data-composer-placement="home"`(보임) · `"thread"`(0×0, 숨음). 우리는 보이는 것을 먼저 고르므로 맞다.

## 고친 것

1. **(0.31.3) 다른 대화로 옮기면 화면 진단 줄을 비운다** (`index.js` 주소 틱 → `GT.skin.current.clearSystem()`).
   판정은 `GT.tabs.leftConversation(from, to)` — 대화(`/c/<id>`)에서 떠나거나 대화가 아닌 화면으로 가면 '옮김'.
   새 대화 화면에서 대화가 막 생긴 것(`/` → `/c/<새 id>`)은 같은 대화라 둔다 — 첫 메시지의 '안 보내졌다' 경고가 이때 2초 뒤에 뜬다
   - **(0.31.5) 임시 대화 주소** — 0.31.4 로 새 채팅에서 보내 보니 주소가 먼저 `/c/local-chatgpt%3A<uuid>` 가 됐다 `[확정]`.
     여기서 진짜 `/c/<id>` 로 바뀌는 것도 같은 대화로 본다(`/c/local-` 로 시작하면 임시). 그대로 두면 `/c/A → /c/B` 로 읽혀 첫 메시지의 경고가 지워진다.
     임시 → 진짜 주소로 바뀌는 순간은 아직 보지 못했다 `[미정]` — MCP 탭이 숨은 탭이라 원본의 `sentinel/chat-requirements/prepare` 가 198초 넘게 끝나지 않아 실제 대화 요청까지 가지 못했다.
     사용자 대화 `6ad16ff2…` 가 진짜 id 주소인 것으로 보아 언젠가 바뀌는 것은 맞다
2. **(0.31.4) not-sent 기록에 어떻게 눌렀는지 남긴다** — `send: { via, waitMs, chars, lines }`.
   `via` 는 `button` · `enter-disabled`(버튼은 있었는데 잠김) · `enter-no-button`. 글 내용은 넣지 않는다

검사: `tabs` 10건 · `route` 2건 · `compose` 5건. 고친 줄을 하나씩 되돌리면 각각 실패.

## 남은 것 `[미정]`

- **18:59 의 진짜 미전송 1건** — 여러 줄 긴 글. 2초 뒤에도 보내기 버튼이 있었고 중지 버튼은 없었다.
  눌렀는지(버튼이 잠겨 Enter 흉내로 넘어갔는지)를 그때 기록하지 않아 가릴 수 없다. 다음에 나면 보고서의 `send.via` 로 가린다
  - 재현 시도(2026-10-16, 0.31.7, 승인받은 6줄 시험 글, '세우다' 대화, 스킨 입력줄 Enter): **정상 전송** —
    1211ms 보내기 버튼 클릭(잠김 아님) → 2210ms 원본 입력창 0자 · 중지 버튼 → 답 끝. 경고 0.
    여러 줄 · 긴 글 자체가 원인은 아니다 `[확정]`
  - **대화 원본으로 그 순간을 되짚었다** `[확정]` (기록 시각 T = 10-15 09:59:22 UTC, 대화 `6acee9…`, 값은 길이만):

    ```
    T−85s  user 109자 2줄            보내짐
    T−83s  assistant (gpt-6-thinking) 345자 · T−74s 에 끝남(finish stop)
    T−3s   (스킨에서 보냄 → 2초 뒤 not-sent 기록: 입력창에 글 · 보내기 버튼 있음 · 중지 버튼 없음)
           서버에 이 시각의 user 메시지 없음 — 정말 안 보내졌다
    T+32s  user 209자 3줄            보내짐 (사용자가 다시 보낸 것으로 본다 [가정])
    ```

    원본은 답을 만들고 있지 않았다(직전 답은 74초 전에 끝남). 즉 '답변 중이라 막힘' 이 아니라 **누른 것이 원본에 먹히지 않았다**.
    왜 먹히지 않았는지(클릭이 무시됐는지 · 버튼이 잠겨 Enter 흉내로 넘어갔는지)는 그때 기록이 없어 `[미정]`
  - **고친 것 (0.32.0, 사용자 결정 2026-10-16)**: 정상 전송 실측 5번은 모두 누르는 즉시 입력창이 비고 60ms 안에 중지 버튼이 떴다.
    그래서 누르고 1.5초 뒤에도 '글 그대로 · 중지 버튼 없음 · 보내기 버튼이 눌릴 수 있음' 이면 클릭이 먹히지 않은 것으로 보고
    **한 번만 다시 누른다**(`send-retried` 로 기록). 버튼이 잠겨 있으면 Enter 흉내로 넘어가지 않고 최대 5초까지 기다린다.
    예전 원칙('자동으로 다시 누르지 않는다 — 늦게 비우는 것뿐이면 두 번 보내진다')을 바꾼 것이다 — 세 조건 중 하나라도 아니면 누르지 않는다
  - **실제 크롬 확인 (0.32.0, `:reload` 뒤 tap 세대 2)**: 승인받은 6줄 시험 글을 '세우다' 대화에 스킨 입력줄로 보냈다 —
    보내기 클릭 1번(다시 누르지 않음) · 서버의 같은 글 1 → 2(정확히 하나 늘었다) · 경고 없음 `[확정]`.
  - **'클릭이 먹히지 않는' 상황을 실제 ChatGPT 에서 만들어 확인 (0.32.0)** `[확정]`: 승인받은 새 채팅 질문(付く와 付ける)을 스킨으로 보내면서,
    페이지의 window 캡처 단계에서 **첫 번째 보내기 클릭만** stopImmediatePropagation + preventDefault 로 버렸다(원본은 그 클릭을 보지 못한다).

    ```
    999ms   클릭 #1 버림
    1000ms  원본 입력창 25자 그대로 · 중지 버튼 없음      ← 사용자 탭 18:59 의 모양
    4000ms  클릭 #2 (0.32.0 다시 누르기, 숨은 탭이라 1.5초 타이머가 늦게 돎) → 통과
    5001ms  입력창 0자 · 중지 버튼 · /c/local-… → /c/6ad190b…
    서버: 사용자 메시지 1 · 답 1 · '안 보내졌다' 경고 없음
    ```

    원본이 왜 클릭을 받지 않았는지(18:59 건의 근본)는 기록이 없어 `[미정]` — 0.32.0 부터는 다시 누르면 `send-retried` 로, 그래도 안 되면 `not-sent` 에 `send.via` · `retried` 가 남는다
  - **원인 후보 정리** — 0.31.2 의 보내기 경로에서 '글이 남는' 길은 둘뿐이다(코드):
    1. 보내기 버튼을 눌렀는데 원본이 받지 않았다 → 0.32.0 다시 누르기가 살린다 (실제 ChatGPT 에서 클릭 무시를 만들어 확인 `[확정]`)
    2. 버튼이 1.5초 넘게 잠겨 Enter 흉내로 넘어갔다 — 원본은 흉내 낸 Enter 를 무시한다(10-15 실측 `[확정]`) → 0.32.0 은 잠긴 버튼을 5초까지 기다린다 (검사로 확인)
    어느 쪽이었는지는 그때 기록(`send.via`)이 없어 가릴 수 없다 `[미정]`. 두 길 모두 막았다
  - **기각한 가설**: 한글 조합(IME) 상태가 원본 입력창에 남아 보내기가 무시된다 — 원본 입력창에 compositionstart 를 걸어 둔 채 눌러도
    정상 전송됐다(2026-10-16, 새 채팅, 승인받은 질문) `[확정 — 합성 이벤트 기준. 실제 OS IME 와 같은지는 미확인]`
