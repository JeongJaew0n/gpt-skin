# 응답의 마지막 문장·글자가 자주 잘린다

답이 끝까지 왔는데 화면에는 뒷부분이 빠져 있다. 새로고침하면 멀쩡하다.

실측: 2026-09-18 · `/c/6aac9ecd-…` 에서 질문 셋을 연달아 보내며 관측

**두 번 `[미정]` 으로 미뤄 둔 건이다.**
[2026-09-09 §2](2026-09-09-url-marker-dropped.md) 와 [2026-09-15 §4](2026-09-15-drift-warning-on-most-chats.md).
이번에 원인을 확정했다.

---

## 1. 결론

**`verify` 의 전제가 틀렸다.**

```js
// index.js
// fiber 원문이 정답이다. 먼저 화면을 교정하고, 대조는 경고 목적으로만 한다.
rec.text = fiber;
```

fiber 는 정답이 아니다. **원본이 화면에 그리다 만 조각인 경우가 흔하다.**
그 조각으로 우리 본문을 덮어쓰니 뒤가 잘린다.

---

## 2. 무엇을 봤나

같은 대화에서 질문 셋을 연달아 보내고, 끝난 뒤 세 응답을 한꺼번에 쟀다.

| 응답 | 원본 fiber | 원본 `innerText` | 우리(SSE) | API 원문 |
|---|---|---|---|---|
| ① 사계절 | 152자 | 146자 | 146자 | 152자 |
| ② 12달 | **38자** | **38자** | **446자** | — |
| ③ 조선 8도 | **1자** | **1자** | **522자** | — |

②③ 에서 **원본 DOM 이 조각**이다. `fiber` 만의 문제가 아니라 `innerText` 도 같으므로
**DOM 자체가 그만큼만 그려져 있다.**

우리 쪽은 셋 다 온전했다. ②의 끝은 `…새해를 준비하는 열두째 달입니다.` 로 지시대로 끝났다.

### 가상 스크롤이 아니다

화면 밖이라 비워 둔 것인가 싶어 맨 아래로 스크롤하고 다시 쟀다.

```
스크롤 후 →  152자 · 38자 · 1자   (그대로)
```

**채워지지 않는다.** 원본의 렌더가 그 상태로 멈춰 있다.

---

## 3. 그래서 왜 잘리나

`index.js` 의 verify 경로다.

```js
setTimeout(() => GT.toMain('verify', { id: p.id }), 400);   // 스트림 종료 400ms 뒤
…
const tooShort = sLen > 0 && fLen < sLen * VERIFY_MIN_RATIO;  // 0.5
if (tooShort) { …재시도… }
rec.text = fiber;        // ← 여기서 화면이 fiber 로 바뀐다
```

`VERIFY_MIN_RATIO = 0.5` 는 **절반 미만만** 걸러낸다.

```
fiber 가 스트림의  0~49%   →  재시도 (최대 3번), 그래도 짧으면 스트림 유지   ✅
fiber 가 스트림의 50~99%   →  통과. rec.text = fiber 로 덮어쓴다            ❌ 여기서 잘린다
```

이번 재현에서는 fiber 가 1자·38자로 **너무 짧아서 오히려 걸러졌다**(0.7%, 8.5%).
그래서 화면이 멀쩡했다. **잘리는 것은 fiber 가 50~99% 로 어중간할 때다** —
원본이 거의 다 그렸지만 마지막 문장을 아직 안 붙인 순간이 그렇다.

사용자가 겪는 빈도로 보아 그 구간이 자주 발생한다.

### 왜 하필 마지막 문장인가

부분 렌더는 **앞에서부터 채워진다.** 그러므로 빠지는 것은 늘 뒤쪽이다 —
"마지막 문장", "마지막 글자" 로 보이는 이유가 이것이다.

---

## 4. 원본 렌더가 왜 멈추나 `[미정]`

원인을 좁히지 못했다. 확인한 것과 못 한 것을 나눠 적는다.

**아닌 것으로 확인됨**
- 가상 스크롤 (맨 아래로 스크롤해도 안 채워짐)
- 우리가 원본을 숨긴 것 (`Ctrl+\`` 로 보이게 한 뒤에도 그대로)

**확인하지 못함**
- `tap.js` 의 `res.body.tee()` — 스트림을 둘로 갈라 원본과 우리가 각각 읽는다.
  한쪽이 늦게 읽으면 다른 쪽에 backpressure 가 걸린다. **가장 유력하다**
- 원본이 백그라운드 탭에서 렌더를 미루는 것

**확인 방법**: 확장을 완전히 끈 상태(`chrome://extensions` 에서 비활성)로 같은 질문을
보내 원본 fiber 가 온전한지 본다. 온전하면 `tee` 가 범인이다.

**다만 원인이 무엇이든 3절의 수정은 유효하다.** fiber 가 조각일 수 있다는 사실
자체가 확정됐고, verify 는 그 가능성을 다루지 못한다.

---

## 5. 고친 것 (2026-09-18 적용 · 0.3.1)

### (1) 짧은 fiber 로는 절대 덮어쓰지 않는다 — 적용

비율을 조이는 게 아니라 **방향을 본다.**

```js
// fiber 가 스트림보다 짧으면 그것은 '교정' 이 아니라 '손실' 이다.
if (strip(fiber).length < strip(streamed).length) return;   // 스트림을 지킨다
rec.text = fiber;
```

fiber 가 **더 길 때만** 덮어쓴다. 그러면 잘림이 원천적으로 사라진다.
fiber 가 정말 교정본인 경우(인용 마커가 치환되어 길어지는 등)는 여전히 받는다.

`VERIFY_MIN_RATIO` 는 없앴다. 이 조건이 상위 집합이다.

실제로 넣은 모양은 이렇다. 짧으면 곧바로 포기하지 않고 **몇 번 더 본다** —
아직 그리는 중일 수 있기 때문이다.

```js
const shorter = sLen > 0 && fLen < sLen;
if (shorter) {
  rec.verifyTries = (rec.verifyTries || 0) + 1;
  if (rec.verifyTries <= VERIFY_RETRIES) { …900ms × 횟수 뒤에 다시… }
  GT.log(`fiber 가 스트림보다 짧다 (${fLen}/${sLen}) — 스트림 본문을 지킨다`);
  return;
}
rec.text = fiber;   // 여기까지 왔으면 fiber 가 같거나 더 길다
```

**드리프트 경고도 같이 조용해진다.** `reconcile` 은 이 뒤에서만 불리므로
조각 fiber 와 온전한 스트림을 비교하는 일이 없어진다 — 2026-09-15 §4 의 남은 오탐이 이것이었다.

### (2) 정본을 fiber 가 아니라 API 로 바꾼다 — 하지 않았다

`/backend-api/conversation/<id>` 가 진짜 정본이다. 우리는 이미 `pull()` 로 읽는다.
fiber 는 "원본이 화면에 그린 것" 일 뿐이다.

이미지 2단계에서 같은 판단을 했다 — 스트림으로 안 오는 것은 API 를 다시 읽어 채웠다
([이미지 생성](../plan/2026-09-09-image-generation.md) 2단계). 같은 길이다.

비용: 턴마다 API 요청이 한 번 더 는다. **(1) 로 잘림은 사라졌으므로 보류한다.**

### (3) 4절을 확인한다 — 남아 있다

`tee` 가 범인이면 그쪽을 고치는 것이 근본이다. 원본 렌더를 망가뜨리고 있다면
드리프트 경고·수확 등 다른 곳에도 영향이 간다.

---

### 검증

`test/verify.test.mjs` 가 **소스에서 핸들러를 통째로 꺼내 실제로 돌린다.**
다시 쓰면 아무것도 검증하지 못한다.

```
1자 fiber 로 522자를 덮어쓰지 않는다      ← 실측값 그대로
80% 짜리 조각도 덮어쓰지 않는다           ← 예전에는 통과하던 구간
한 글자 모자라도 덮어쓰지 않는다
더 길면 교정한다 · 같은 길이면 교정한다
스트림이 비었으면 fiber 를 쓴다
빈 fiber 로 화면을 비우지 않는다
조각 fiber 로 드리프트 경고를 내지 않는다
```

판정을 예전(50% 비율)으로 되돌리면 5건이 깨지는 것까지 확인했다.

## 회귀 방지

- fiber 가 스트림보다 짧으면 화면을 바꾸지 않는가
- fiber 가 더 길 때는 여전히 교정하는가 (인용 마커 치환 등)
- fiber 가 비어 있을 때 화면을 비우지 않는가
- 스트림이 비어 있고 fiber 만 있을 때는 fiber 를 쓰는가
