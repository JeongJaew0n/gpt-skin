# 새로고침 직후 단축키가 안 먹는다

새로고침하면 `Ctrl+\`` 나 다른 단축키가 안 먹는다. 툴바 팝업으로 직접 켜 주면 그때부터 먹는다.

조사·수정: 2026-09-28 · 0.11.1 · 0.11.2 (§4 · §5)

---

## 1. 원인 `[확정]`

단축키 리스너(`GT.skin.attachPrompt()`)와 팝업 토글을 받는 리스너(`chrome.runtime.onMessage`)가
**부팅 점검 대기 뒤에** 연결됐다.

```
스킨 붙이기 → waitTap(최대 5초) → 컴포저 대기(최대 15초) → 스레드 대기(최대 15초)
            → 그제야 단축키 · 팝업 연결
```

점검은 "원본이 멀쩡한가" 를 보는 것이고 키를 받을 준비와는 상관이 없다. 그런데 점검이 끝날 때까지
최대 35초 동안 단축키도 팝업도 먹지 않았다. 컴포저를 찾지 못하는 화면이면 15초를 꼬박 기다린다.

"팝업으로 켜면 그때부터 먹는다" 는 것은, 팝업을 누를 즈음엔 이미 점검이 끝나 있었기 때문이다.
팝업이 뭔가를 풀어 준 게 아니다.

## 2. 실측

실제 ChatGPT 에 확장을 올려 새로고침 직후부터 `Ctrl+\`` 를 눌렀다. 헤드리스는 Cloudflare 확인 화면
("잠시만 기다리십시오…")에 막혀서, 화면 밖에 띄운 일반 크롬(별도 프로필, 비로그인)에 CDP
`Extensions.loadUnpacked` 로 올리고 `Input.dispatchKeyEvent` 로 진짜 키를 보냈다.

**고치기 전** (2초 간격)

```
  2312ms ~ 13852ms   안 먹힘 (6번)
 16164ms ~           먹힘
```

이 화면(비로그인)에는 `#prompt-textarea` 가 없고 입력창이 `textarea#mobile-composer-prompt` 라서
컴포저 대기가 15초를 다 채웠다.

**고친 뒤**

```
   461ms   Ctrl+`  먹힘
  1076ms   Ctrl+`  먹힘
  2054ms   팝업 toggle 먹힘 (서비스워커 → 탭 sendMessage, 팝업이 보내는 것과 같은 메시지)
```

### 가설 하나를 버렸다

처음에는 "새로고침 직후 ChatGPT 가 컴포저에 초점을 주고, 페이지가 keydown 을 `stopPropagation` 해서
`window` 버블 단계의 우리 리스너까지 안 온다" 고 봤다. 부팅이 끝난 뒤 입력창에 초점을 두고 눌러 보니
window 의 캡처·버블 단계 모두 키가 도착했고 토글도 됐다. **이 화면에서는 페이지가 키를 막지 않는다.**
(로그인 화면의 컴포저는 다른 요소라 따로 확인하지 않았다 `[미정]`)

## 3. 고친 것

- `index.js` — `attachPrompt()` 와 `chrome.runtime.onMessage` 를 **스킨을 붙인 바로 뒤, 점검 대기 앞**으로 옮겼다
- `prompt.js` — 키가 점검보다 먼저 붙으므로, 점검이 실패해 원본으로 돌아간(degraded) 뒤에는 `Ctrl+;` 가
  다시 열지 않게 했다. `Ctrl+\`` 경로(`skin.toggle`)는 이미 거절하고 있었다

## 4. 켜 둔 화면을 점검 전에 켠다 (0.11.2) `[확정]`

0.11.1 에서는 단축키만 앞으로 옮기고, **자동으로 켜지는 것(`enabled` · 교대 상속)은 점검 뒤에 두었다.**
그래서 켜 둔 화면이 새로고침·재주입 뒤 점검 시간만큼 원본으로 보였다.

- 설정 `onBreak` 가 기본값(`revert` 가 아님)이면 **단축키 연결 바로 뒤에 켠다.** 점검이 실패해도 원본으로
  되돌리지 않는 설정이라, 먼저 켜도 켜졌다 꺼지는 깜빡임이 없다
- `onBreak = revert` 면 예전처럼 **원본 복귀 판정 뒤에** 켠다. 먼저 켜면 점검 실패 화면에서 깜빡인다

실측(비로그인 ChatGPT, 화면 밖 일반 크롬, 새로고침 → 화면이 보일 때까지)

```
0.11.1   15531ms
0.11.2     177ms
```

## 5. 비로그인 화면의 입력창 (0.11.2) `[확정]`

비로그인 화면의 입력창은 `#prompt-textarea`(ProseMirror)가 아니라 평범한 textarea 다.

```
textarea#mobile-composer-prompt  name="prompt"
보내기 버튼  aria-label="메시지 보내기"  type=submit  (비어 있어도 활성)
```

`compose.js` 가 `#prompt-textarea` 만 봐서 이 화면에서는 넣기가 실패했고, 부팅 점검도 컴포저를 못 찾아
15초를 채웠다.

- 입력창 목록을 `compose.js` 한 곳에 둔다 — `#prompt-textarea` → `textarea#mobile-composer-prompt` → `textarea[name="prompt"]`.
  부팅 점검도 같은 목록(`GT.compose.SELECTOR`)으로 기다린다
- textarea 는 React 가 값을 들고 있어 `value` 를 그냥 대입하면 무시된다. `execCommand('insertText')` 로 넣고,
  안 먹으면 프로토타입의 원래 setter 로 넣고 `input` 을 쏜다
- **보낸 뒤 2초에 원본 입력창을 본다.** 보낸 글이 그대로 남아 있으면 "원본이 보내지 않았습니다" 를 찍는다.
  자동으로 다시 누르지는 않는다 — 원본이 늦게 비우는 것뿐이면 두 번 보내진다

실측(별도 비로그인 프로필, 우리 입력줄에 글을 치고 Enter)

```
고치기 전   #prompt-textarea 가 없음(실측) → composer() 가 null 이라 넣기 실패 (코드로 판단, 보내기는 시험 안 함)
고친 뒤     3번 연속 보냄 — POST /unauth-mweb/conversation/prepare · updates, 주소가 /uc/<id> 로 바뀜,
            원본 입력창 비워짐, 미전송 경고 없음
```

조사 중 한 번은 넣고 눌렀는데 POST 가 없고 글이 남았다. 그 뒤로는 재현되지 않았다. 원인은 모른다 `[미정]` —
그래서 위의 미전송 경고를 넣었다. 다시 나오면 경고로 보인다.

### 남은 것

- **비로그인 화면의 답은 우리 화면에 안 그려진다** `[확정]` — 비로그인 대화는 `/unauth-mweb/…` 로 오가는데
  tap 은 `/backend-api/f/conversation` 만 본다. 보낸 글도 우리 화면에 안 나온다. 비로그인 지원은 이번 범위가 아니다
- **로그인 화면의 입력창은 이번에 확인하지 않았다** `[미정]` — 목록 첫 자리는 예전과 같은 `#prompt-textarea` 라
  로그인 화면의 동작은 바뀌지 않았다(코드상). 확인하려면 로그인 탭에서 `:version` 이 0.11.2 인지 보고 한 번 보내 본다
- 한 번 본 "넣고 눌렀는데 안 보내짐" 의 원인 `[미정]`

## 회귀 방지 — `test/shortcuts.test.mjs`

- 단축키·팝업 연결이 tap·컴포저·스레드 대기와 원본 복귀 판정보다 **앞**에 있는가 (주석을 뺀 코드에서 위치를 잰다)
- 연결은 한 번뿐인가 · 물러날 때 떼는가
- 원본 복귀 상태에서 `Ctrl+;` · `Ctrl+\`` 가 다시 열지 않는가
- 기본값이면 자동 켜짐이 점검 대기보다 앞, `revert` 면 원본 복귀 판정 뒤인가
- `test/compose.test.mjs` — 두 입력창을 찾아 넣는가 · 보낸 뒤 글이 남으면 알리고 다시 누르지 않는가

직전 판의 `index.js` 로 돌리면 5건이 깨지는 것을 확인했다. 기존 테스트 1501건은 순서를 전혀 보지 않아
이 버그를 잡지 못했다.
